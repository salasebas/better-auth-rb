Use dynamic `base_url` when your app serves requests from several hostnames, such as custom domains, preview deployments, or branch environments.

## Basic setup

Set `base_url` to a hash with a nonempty `allowed_hosts` list.

```ruby
require "better_auth"

auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["myapp.com", "www.myapp.com", "preview-*.myapp.com"]}
)
```

RubyAuth checks `X-Forwarded-Host`, then `Host`, then the request URL's host. The selected host must match an entry in `allowed_hosts`, including the port if present.

Dynamic configuration trusts forwarded host and protocol headers by default. Use `advanced: {trusted_proxy_headers: false}` if clients can reach the Rack server directly or your proxy passes through client-supplied forwarding headers.

## Common deployment patterns

### Vercel deployment

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["myapp.com", "my-app-*.vercel.app"]}
)
```

### Development and production

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {
    allowed_hosts: ["localhost:3000", "myapp.com"],
    protocol: ENV["RACK_ENV"] == "production" ? "https" : "http"
  }
)
```

### Multiple production domains

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["myapp.com", "myapp.co.uk", "myapp.eu"], protocol: "https"}
)
```

## Choosing a fallback

RubyAuth raises when the request host is missing or outside `allowed_hosts`. Set `fallback` to use a configured URL in those cases.

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["myapp.com", "preview-*.myapp.com"], fallback: "https://myapp.com"}
)
```

Pass the incoming Rack request to a direct `auth.api` call, or pass headers that include a host.

```ruby
auth.api.get_session(headers: {"host" => "myapp.com"})
```

Direct calls without a request or host headers use `fallback`. If there is no fallback, the call raises `BetterAuth::APIError` with status `INTERNAL_SERVER_ERROR`.

## Cookies across subdomains

When `cross_subdomain_cookies` is enabled, RubyAuth uses the resolved hostname as the cookie domain.

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["auth.example.com", "preview.example.com"], protocol: "https"},
  advanced: {cross_subdomain_cookies: {enabled: true}}
)
```

Set `domain` to share cookies across a specific parent domain.

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: {allowed_hosts: ["auth.example.com", "preview.example.com"], protocol: "https"},
  advanced: {cross_subdomain_cookies: {enabled: true, domain: ".example.com"}}
)
```

See [Cookies](/docs/concepts/cookies#cross-subdomain-cookies) for cookie behavior.

## Security model

Use exact hosts or patterns that match only domains you control. RubyAuth uses the resolved URL for OAuth callbacks and token-bearing links. It expands allowed hosts into trusted origins according to `protocol` and adds the fallback origin when configured. Add frontend-only origins to `trusted_origins`.

For a fixed issuer and provider callback URL, configure a static `base_url` and use the Ruby-only `serving_origins` option for request-facing links.

```ruby
auth = BetterAuth.auth(
  secret: ENV.fetch("BETTER_AUTH_SECRET"),
  base_url: "https://auth.example.com",
  serving_origins: ["https://tenant.example.com", "https://*.preview.example.com"],
  trusted_origins: ["https://frontend.example.com"]
)
```

RubyAuth requires a configured URL or an allowlist at startup so an incoming request alone cannot select the host used in token-bearing links.
